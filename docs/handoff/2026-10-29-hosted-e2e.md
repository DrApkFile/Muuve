## Defects found and local fixes

1. **Authenticated missing-operation lookup returned empty HTTP 500.**
   `apps/web/lib/server/router.ts`, operation GET branch, returned `transaction(...)`
   without awaiting it inside the error handler. A rejected authorization/not-found
   check escaped the JSON error boundary. Fixed by awaiting the transaction. The new
   API regression failed before the fix, then passed for both missing and foreign
   operations; the actual owner can still retrieve their operation. Hosted evidence:
   `evidence/hosted-e2e/unknown-operation.json`.
2. **Unlinked Privy user returned HTTP 500.** The live server rejected the arbitrary
   CLI wallet and left the account unlinked, but exposed an inappropriate generic 500.
   A direct read-only Privy lookup confirmed 404 for the test custom-auth identity.
   `apps/web/lib/server/providers/privy.ts` now maps missing users to 403
   `wallet_not_owned`, and provider/transport failures to redacted 503
   `privy_unavailable`. SDK calls have a 10-second timeout and no internal retries.
   Six new unit cases failed before the fix and all 11 ownership tests passed after it.
   Existing identity, wallet, chain and embedded-wallet checks remain mandatory.
3. **Missing Render public CA file.** Fixed by the owner's dashboard upload and
   positively retested against Render; no application TLS weakening was needed.

The two source fixes are **local and tested, not deployed to Render**. No commit,
push, hosted deployment or production configuration change was made by this verifier.
A new Render deployment and authenticated retest are required before declaring those
hosted defects resolved. The initial account probe incorrectly described an empty
non-JSON 500 as a transport/parsing failure; `unknown-operation.json` isolates the
actual HTTP outcome. Both preliminary artifacts are retained rather than hidden.

under **Integrations > Built-in**, then open **User management > Authentication >
JWT integration**. For the existing bridge contract, supply the JWKS endpoint
`https://muuve.onrender.com/api/auth/jwks` and ID claim `sub`. Select the authentication
environment to match the reviewed wallet consumer: enable client-side only when the
consumer actually authenticates via a Privy client SDK. This verifier did not change
any setting or create a signing wallet. Muuve's tested JWT issuer is
`https://muuve.onrender.com`, audience is the configured Privy App ID, subject is the
Muuve user UUID, and algorithm is ES256; no undocumented dashboard fields are assumed.
