# Frontend handoff — 31 October 2026

First browser frontend, built inside `apps/web` so pages and API share one origin
(satisfies the same-origin/cookie prerequisite in `docs/frontend-integration.md`).
Nothing here has been exercised against the hosted API with a real wallet or phone yet.

## Done

| Route            | What it does                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| `/`              | Landing: hero, How it works, footer                                                                |
| `/start`         | Sender sign-in: wallet connect → challenge → sign → login, then phone verify (`/api/me/phone`)     |
| `/home`          | Dashboard: balance (mock-rate label), segment bar, weekly sends, next return ring, links, timeline |
| `/send`          | Single or batch (1–10): validation, split equally, claim-key derivation, prepare → sign → submit   |
| `/send/[id]`     | Share: WhatsApp/copy/native share; re-derives `#k=` from the wallet if not in memory               |
| `/activity`      | Sender links with filters                                                                          |
| `/activity/[id]` | Per-recipient status, recall one / recall all, reminder, timeline, expiry ring                     |
| `/cashout`       | Account cash-out (quote → bank/resolve → prepare → wallet sign → submit → payout polling), gated   |
| `/c/[id]`        | Recipient claim: key → preview → SMS OTP → share → cash out (bank → payout) or keep (account)      |
| 404              | `app/not-found.tsx`                                                                                |

Client layer: `lib/api.ts` (typed client, `{ error, request_id }`; calls go to the site's own `/api/*`
route, `lib/server/forward.ts`, which runs the API handler in-process or forwards server-side to
`MUUVE_API_URL` with cookies, origin and client IP, so the browser never talks to the API host.
A route, not a server action: Next runs server actions one at a time, which queued taps behind polling), `lib/wallet.tsx` (Wallet
Standard, signMessage + signTransaction only), `lib/session.tsx` (`/api/me`, 401 → `/start`,
refresh ≤ twice a day, logout), `lib/solana.ts` (exact-transaction signing, claim key,
operation polling), `lib/format.ts` (BigInt money, split, masking), `lib/errors.ts` (code → copy).

## Decisions

- Claim key: wallet signs `muuve-claim-v1:{link_id_hex}`, seed = SHA-256(signature),
  `Keypair.fromSeed`. Secret lives in the URL fragment and in memory only.
- Links use the API UUID in `/c/{id}`; `link_id_hex` is never used in URLs.
- Retries reuse the same link ID, request body, operation ID; a fresh signature gets a fresh
  idempotency key. Rejected/stale signatures (`transaction_message_mismatch`, etc.) re-sign.
- Phone account sign-up UI was removed from `/start`; phone OTP now lives on the claim page.
- `@solana/web3.js` is lazy-loaded on the claim page (only when the recipient confirms).

## Accounts and phones

- Wallet sign-ups have no phone. `/start` asks for one right after wallet login: account OTP
  (`purpose: "account"`) then `POST /api/me/phone { challenge_id, code }`, which attaches the
  verified number to the signed-in user (no cookies issued; `phone_in_use` if another account
  has it). `/api/me` now returns `phone_linked` and `phone_last4`.
- Funding, link creation and account cash-out return `phone_required` (403) until a phone is
  linked; recall stays open so senders can always get money back. The app shell sends
  signed-in users without a phone back to `/start`.
- Phone sign-in on `/start` ("Kept dollars with Muuve?") is for recipient accounts.

## Keep in dollars

- Claim page → Keep → `/api/me`; if 401, the recipient enters a name and
  `POST /api/auth/signup` turns the claim session into an account for that number.
- `POST /api/auth/wallet/embedded` returns the user's wallet; if none, the server creates (or
  finds) the Privy user for the Muuve user ID as `custom_auth` and pregenerates a Solana
  embedded wallet, then links it through the existing Privy ownership check.
- Then intent (`path: "keep"`) and `keep/prepare` → claim-key signature → `keep/submit`.
  The claim key signs; the new wallet never has to sign.
- Not yet: cashing out or sending from a Privy embedded wallet (needs Privy-side signing).

## Testing

- `pnpm test:e2e:local [--keep]` runs the API in-process on a disposable loopback Postgres
  against real devnet with mock OTP/payouts: sender wallet login → phone link → test dollars
  → link → recipient OTP → cash-out intent → bank → payout paid. `--keep` adds a second
  recipient who keeps dollars (creates a real user in the configured Privy app). Needs
  `apps/web/.env.local` for devnet keys and `initdb`/`pg_ctl` on PATH.

## Flags (public, build-time)

- `NEXT_PUBLIC_CLAIMS_ENABLED=true` — enables recipient cash-out, keep and `/cashout`. Set in
  `render.yaml` and in `pnpm dev`.
- `NEXT_PUBLIC_WHATSAPP_OTP_ENABLED` — unused while Textbee is SMS-only.

## Known issues / next

- Wallet-only users are named "Wallet sender"; recipients see "Wallet sent you money".
  Needs a display-name endpoint on the backend.
- Payouts are still the mock provider. A real provider must not go live while senders can
  mint free devnet test dollars: that would pay real naira for test tokens.
- Claim page first load is ~223 KB gzip: ~150 KB is the React/Next runtime, ~50 KB app code.
  The 150 KB guide budget is not reachable with this framework baseline.
- `/api/public/links/{id}` returned 500 against the local dev environment (backend/DB config),
  so the claim flow has only been checked for its error state locally.
- No Open Graph image for `/c/[id]` yet; preview is fetched client-side.
