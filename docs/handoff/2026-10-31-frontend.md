# Frontend handoff — 31 October 2026

First browser frontend, built inside `apps/web` so pages and API share one origin
(satisfies the same-origin/cookie prerequisite in `docs/frontend-integration.md`).
Nothing here has been exercised against the hosted API with a real wallet or phone yet.

## Done

| Route            | What it does                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| `/`              | Landing: hero, How it works, footer                                                                |
| `/start`         | Sender sign-in: Wallet Standard connect → `/api/auth/wallet/challenge` → sign → `/wallet/login`    |
| `/home`          | Dashboard: balance (mock-rate label), segment bar, weekly sends, next return ring, links, timeline |
| `/send`          | Single or batch (1–10): validation, split equally, claim-key derivation, prepare → sign → submit   |
| `/send/[id]`     | Share: WhatsApp/copy/native share; re-derives `#k=` from the wallet if not in memory               |
| `/activity`      | Sender links with filters                                                                          |
| `/activity/[id]` | Per-recipient status, recall one / recall all, reminder, timeline, expiry ring                     |
| `/cashout`       | Account cash-out (quote → bank/resolve → prepare → wallet sign → submit → payout polling), gated   |
| `/c/[id]`        | Recipient claim: fragment key → preview → SMS OTP → share → cash-out intent → bank → payout, gated |
| 404              | `app/not-found.tsx`                                                                                |

Client layer: `lib/api.ts` (typed client, `{ error, request_id }`; every call runs server-side through
the `serverCall` action in `lib/server-call.ts`, which invokes the API handler in-process and
forwards cookies, origin and client IP, so the browser never fetches `/api/*` itself), `lib/wallet.tsx` (Wallet
Standard, signMessage + signTransaction only), `lib/session.tsx` (`/api/me`, 401 → `/start`,
refresh ≤ twice a day, logout), `lib/solana.ts` (exact-transaction signing, claim key,
operation polling), `lib/format.ts` (BigInt money, split, masking), `lib/errors.ts` (code → copy).

## Decisions

- Claim key: wallet signs `muuve-claim-v1:{link_id_hex}`, seed = SHA-256(signature),
  `Keypair.fromSeed`. Secret lives in the URL fragment and in memory only.
- Links use the API UUID in `/c/{id}`; `link_id_hex` is never used in URLs.
- Retries reuse the same link ID, request body, operation ID; a fresh signature gets a fresh
  idempotency key. Rejected/stale signatures (`transaction_message_mismatch`, etc.) re-sign.
- Phone account sign-up UI was removed from `/start`; phone OTP now lives on the claim page.
- `@solana/web3.js` is lazy-loaded on the claim page (only when the recipient confirms).

## Flags (public, build-time)

- `NEXT_PUBLIC_CLAIMS_ENABLED=true` — enables recipient cash-out and `/cashout`. Off by
  default per the integration guide until hosted recipient/treasury/worker checks pass.
- `NEXT_PUBLIC_WHATSAPP_OTP_ENABLED` — unused while Textbee is SMS-only.
- Keep in dollars is hard-disabled (`KEEP_ENABLED = false`) until Privy enrollment works.

## Known issues / next

- Wallet-only users are named "Wallet sender"; recipients see "Wallet sent you money".
  Needs a display-name endpoint on the backend.
- Claim page first load is ~223 KB gzip: ~150 KB is the React/Next runtime, ~50 KB app code.
  The 150 KB guide budget is not reachable with this framework baseline.
- `/api/public/links/{id}` returned 500 against the local dev environment (backend/DB config),
  so the claim flow has only been checked for its error state locally.
- No Open Graph image for `/c/[id]` yet; preview is fetched client-side.
